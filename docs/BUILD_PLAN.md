## P0：一次建立清楚的环境

优先使用 Ubuntu 22.04 自带 /usr/bin/python3 建立项目 .venv，MuJoCo 固定 3.3.0 作为已审阅解析行为的版本，不声称它是最新版。依赖只安装到项目内。若 python3-venv 缺失，处理实际系统包缺项即可，不重装 ROS/CUDA。

scripts/project_env.sh 使用最小环境，保留桌面显示、代理和证书路径等必要设置。不要用它启动需要 ROS Python 路径的节点；Xacro/RViz 若需要，另开一个仅 source ROS2 Humble 的终端。初期不必启动 ROS graph。

## H0：增加一次机械臂与腕部相机联合运行

执行 docs/HARDWARE_INTEGRATION.md 与 prompts/HARDWARE_INTEGRATION.txt。现有 Piper H 本体验机结果继续有效；新增工作是相机接入，以及开启取流后机械臂状态、图像、深度和夹爪变化能否同时稳定记录。

在现有固定安装条件下进行，不需要先装到 M1。复用原机械臂环境，独立运行相机 ROS workspace；scripts/hardware_env.sh 用于加载已有 ROS 与指定 overlay，不替代原有机械臂控制环境。先静止联合采集，再用当前已验证的控制方式做少量低速小幅动作，由现场操作者启动；保持唯一运动命令发送端。

实际记录两路 CameraInfo、流模式、原始深度单位、真实反馈和同一主机接收时间，观察遮挡、线缆、掉流与资源竞争。保留短视频及可分析的数据，不能以视频替代原始深度和状态。报告中区分软件时间关联、手眼外参、视觉闭环。

H0 不要求标定板或附件称重，也不把未连接实机变成 P0–P3/P4 名义仿真的硬门槛。硬件不可用则该项保持 pending；设备可用时完成本轮，不能永久以准备完成代替实测。H0 结果可更新 P3 的视角与实际接口信息，未知外参继续标为名义值。

## P1–P2：正确的源模型比大量依赖重要

M1 默认只下载 model/zgws 子目录，不安装 SDK，不下载 MC 的大二进制 release，不运行厂商加载器。原文件没有地面，注释里的 home 不算有效初始姿态。M1 的 16 个 motor 不接受目标角语义。

Piper H 使用专门目录，带夹爪 Xacro 已包含夹爪。必须处理 package:// 资源路径、DAE 场景变换和唯一 mesh basename。没有 M1 原始 URDF 时可针对已知 MJCF 树生成衍生 URDF，不等待新资料。

如果原始 STL 被 MuJoCo 拒绝，保留形状并转换对应网格。不能删掉出问题的几何后报告模型成功。

## P3：第一轮应到达的明确终点

建议最终输出路径：

- description/m1_derived.urdf
- description/m1_piper.urdf 和可维护的 Xacro/生成脚本
- description/joint_map.yaml
- sim/robots/m1_piper.xml
- sim/scenes/assembly_preview.xml
- reports/assembly_report.md
- results/assembly/front.png、side.png、wrist_detail.png、wrist_rgb.png、wrist_depth_m.npy

生成入口现为 scripts/build_assembly.py；少量 FK 对照入口为 scripts/check_assembly.py；真实桌面查看入口为 scripts/live_assembly.py；离线图片／短片入口为 scripts/capture_assembly.py。带门腕部图像保存在 results/assembly/with_door/，其外参和机器人 home 与空场景一致。

M1 原生 MJCF 继续作为仿真动力学来源；衍生 URDF用于描述、规划或坐标检查。可以在 MJCF 中保留 M1 的 body/joint/inertial/actuator，再接入转换后的 Piper 子树。不要为了得到统一文件而先后多次往返转换所有动力学参数。

整机只能有一个自由基座。M1 背部安装位置先采用 config/assembly.yaml 中的名义值，依据网格实际顶面和碰撞关系调整。腕部支架依据官方几何、孔位与四张照片对齐，不能把旧 Piper 完整组合 mesh 的原点直接当 Piper H 安装外参。

相机/支架暂不计额外载荷；输出报告必须记这一假设，但继续推进基础动力学。第一版虚拟相机可用同一 camera 输出 RGB 和 depth，不等待真实内参。

只做几组有意义的检查：轮心、末端法兰和 TCP 的 FK 对照；左右手指正确开合；手指开合不改变相机相对固定主体的位置；可视/碰撞模型和照片大体对应。不要把验证扩展成大量与当前问题无关的框架。

## P4：MuJoCo 固定基座接触开门

利用 sim/components/door_single.xml 构造固定基座机器人场景。门配置是普通实验门的设计参数，允许调整把手高度与机器人初始位置，使任务在合理工作空间内。

P4 使用从组合模型生成的专用固定基座场景，报告记录固定方式；自由基座主模型继续保留。P5 切回自由基座场景，不把 P4 的固定条件带入移动操作结果。

第一版可直接使用仿真中的门把手真实位姿。建议有限状态流程为：预抓取位、接近、夹持、沿铰链圆弧推进、松开、退离。用已有运动学求解和有限力矩的关节控制实现，必要时加入末端柔顺。无需先引入 RL 或复现整套论文框架。

推、拉分别作为不同接近侧的任务。默认门的正角方向是向世界 −X 开启：关闭时 front（x<1.5）是拉门侧，back（x>1.5）是推门侧。不要让位于 x≈0 的机器人向 +X 推默认关闭门，那会压向 0 角限位。可以改变机器人接近侧，或在场景配置中明确改变门的安装朝向。

目标开角可先设 60°；接触是否有效由门角变化、机器人施力和闭环轨迹共同判断。单次成功只记单次，稳定性需要在明确变化的初始状态下重复。

门没有执行器、闭门弹簧或锁舌，固定把手不需要另加旋转关节。调试时可单独改变 qpos 查看几何，但任务运行不得每步设置门角或把机器人 TCP 焊接到门上。

## P5：释放底盘后的基础控制

先求得合理的支撑姿态和地面高度，用腿部力矩/PD与轮速控制实现静止和慢行。轮轴和正方向须逐个核对，不能假定同一正 ctrl 让四轮都向前。低速前进和转向通过轮足真实动力学实现，不向自由基座 qpos 写轨迹。

先检查展开机械臂时的支撑、俯仰和轮滑，再做自由基座单门操作。需要官方运控时，单独核对 M1/ZGWS 的 state/action 顺序、模式、IMU、时间步和控制频率；存在 ZGWS_ARM 目录不表示已经适配当前 Piper H 组合。

## P6：连续自由基座单门

执行 [P6_SINGLE_DOOR_PLAN.md](P6_SINGLE_DOOR_PLAN.md) 和 [本机提示](../prompts/P6_SINGLE_DOOR.txt)。先使自由底盘在操作站位承重并展开臂，再做小角度至约60°前拉，随后接入短距离驶近和退离。先复用较干净的前拉基线，背推非预期夹爪基座接触单独修正。

P6须统一物理状态与控制写入口，修正P5轮速公式的世界Y假设，用实际沉降后的根姿态求IK，并根据停稳/抓持/门角/释放事件转换阶段。不能顺序调用P5后再进入会固定根并重置状态的P4.run。定义及待验证门槛以P6细化计划为准，不将准备状态写成任务完成。

## P7：双门

双门采用两个独立被动铰链，先开一扇再移动到另一扇合适的接近位。当前完成定义是两扇开至目标并稳定结束；穿过门洞、真实门锁或闭门器可在此基础上增加，不混入当前初始任务。
